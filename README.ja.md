# DocChat

[![CI](https://github.com/JINWORLD13/docchat/actions/workflows/ci.yml/badge.svg)](https://github.com/JINWORLD13/docchat/actions/workflows/ci.yml)

[ライブデモ →](https://docchat-izxf.onrender.com)(Renderの無料枠のため、しばらく
アクセスがないとサーバーがスリープし、初回アクセス時に起動するまで最大1分ほど
かかることがある)

ドキュメント(txt, md)をアップロードすると、その内容だけを根拠に回答する
RAGチャットボット。ここに、複数人が同じルームで会話するリアルタイムチャットも
組み込んだ。TypeScript、React、Express、PostgreSQL(pgvector)、Socket.IO、
Gemini APIで作った。
生成はローカルLLM(Ollama)を先頭に立て、Geminiを最後の砦に置くチェーン構成にも
でき(envの1行)、同じエンジンをカカオトークチャットボット(オープンビルダースキル)
としても公開している。

ひとつのサーバーが2種類のリアルタイムを扱う — 回答トークンはSSE(一方向)、
チャットはWebSocket(双方向1:N)。なぜ分けずに同じプロセスに置いたのかは
[PORTFOLIO.ja.md](PORTFOLIO.ja.md)にまとめた。

> あわせて読む — [PORTFOLIO.ja.md](PORTFOLIO.ja.md): 技術選定とその理由 ·
> [RELIABILITY.ja.md](RELIABILITY.ja.md): 負荷・障害対応の設計と測定値

![回答と根拠の出典](docs/demo-answer.png)

回答の上に参照したドキュメントと類似度が表示され、本文中の [1], [2] がその出典と紐づく。

![ドキュメントになければ拒否](docs/demo-refusal.png)

ドキュメントにない内容なら、でっち上げずに拒否する。このときLLMは呼び出しすらしない。
(質問に画像を添付したときだけ例外 — 根拠が文書から画像へ変わるため拒否しない。
下の「質問への画像添付」を参照。)

![リアルタイムチャット](docs/demo-chat.png)

同じ部屋に入った人同士でメッセージが行き交う。部屋の一覧・接続者・入室の通知・
入力中の表示まで、ソケット1本で処理する。ドキュメントQ&A(SSE)と同じサーバー、
同じポートで動く。

![LLM障害注入時のダッシュボード](docs/demo-dashboard-breaker.png)

ダッシュボードからトラフィックの急増とLLM障害を直接注入し、防御レイヤー(Rate Limiter、
Admission Control、Bulkhead、Circuit Breaker)が反応する様子をリアルタイムで確認できる。
上の画面はLLMが完全に落ちた状態 — 回路はオープンになり、20件中ハードエラーは 0件で、
ユーザーは出典を受け取り続けている。設計の根拠は
[RELIABILITY.ja.md](RELIABILITY.ja.md) へ。

## なぜ作ったか

LLM APIを一度呼んで答えをもらうことと、信頼して使えるAI機能を作ることは
別の問題だと考えた。このプロジェクトは、その違いを自分の手で実装してみるために始めた。
検索(RAG)、根拠の表示、わからないことは「わからない」と答えること、
ストリーミング応答、トークンのロギングまで — 実際のサービスなら必要になるものを、
小さなスコープの中にすべて詰め込んだ。

## 動作の仕組み

```
[ドキュメントのアップロード]
ファイル → 単語単位でオーバーラップさせてチャンキング → 埋め込み(既定はGemini 768次元) → pgvectorに保存

[質問]
質問を埋め込み → コサイン類似度検索 top 5
  → 最高類似度 < しきい値 : 回答を拒否 (LLMを呼ばない)
    (質問に画像が付いていれば拒否しない — 根拠が画像)
  → 通過 : 抜粋をプロンプトに入れて生成 → SSEストリーミング
    (生成器はチェーン — GENERATORS=ollama,geminiならローカル優先、失敗時はGemini)
→ 根拠(出典)とトークン使用量を表示、query_logsに記録

同じエンジンが転送だけ変えて、カカオトークスキル(/api/kakao/skill)でも答える
```

## こだわったポイント

### わからないことは「わからない」と答えさせる

ドキュメントにない質問にもっともらしい答えをでっち上げるのが、RAGの最悪の失敗だと考えた。
検索された最高類似度がしきい値(デフォルト0.62)より低ければ、LLMをそもそも呼び出さずに
拒否する。もっともらしい嘘(ハルシネーション)を防ぎつつ、トークンも節約できる。
しきい値は勘で決めたのではなく、サンプルドキュメントで関連質問(類似度0.66〜0.74)と
無関係な質問(0.53〜0.59)を実測し、その間に設定した。ドキュメントが変わったら、
質問ごとに `query_logs` に残る類似度を見て調整し直す。

例外が1つある — 質問に画像を添付すると拒否しない。このしきい値は「根拠のない回答」を
防ぐためのものだが、スクリーンショットを上げて「このエラー何?」と聞いたとき、根拠は
質問のテキストではなく画像の中にある。テキストの類似度で判定すると正当な質問がすべて
弾かれてしまうため、そのときは抜粋なしで(無関係なチャンクを根拠のふりをして
差し込まず)画像だけを見て答えさせる。根拠がなくなるのではなく、文書から画像へ
変わるのである。

```sql
select question, refused, top_similarity from query_logs order by id desc limit 20;
```

### 回答ごとに根拠を見せる

回答に使った抜粋のファイル名、類似度、プレビューを回答の上に添え、
本文にも [1], [2] の番号を振る。根拠は生成開始前に先に送り出すので、
ストリーミング中でも出典が見える。

### ベクトル検索はpgvectorで

別途ベクトルDBを立てず、Postgresにvectorカラムを置いて `<=>`(コサイン距離)演算子と
HNSWインデックスで検索する。ドキュメントのメタデータとベクトルを一つのDBで
まとめて管理できる点が決め手だった。

### オーバーラップするチャンキング

チャンクの境界で文が切れると検索にヒットしないことがあるため、
単語200個(空白区切り)単位で40個ずつオーバーラップさせて切る。
純粋関数なのでテストを付けてある。

### 過負荷と障害に耐える設計

Rate Limiter(Token Bucket)、Admission Control(同時実行の上限 + 待機デッドライン)、
Bulkhead(コネクションプールをreadPool·writePool·mediaPoolの3つに隔離 —
画像の取得が質問応答を飢えさせないように)、Circuit Breaker(埋め込み・クラウド生成・
ローカル生成それぞれ)、Graceful Degradationを自前で実装した。ボトルネックは推測せず、
実際に負荷をかけて測定し(LLMではなくDBプールだった)、各レイヤーの挙動を単体テストで
固定した。(`cd server && npm test` — 147件)

施策ごとの実測（同時50接続・LLMはmockで隔離）: Admission Controlでプール待機列
88 → 6、回路オープンで障害中の遅延 500 → 190ms（ハードエラー0）、埋め込み
キャッシュはミス1197ms → ヒット0.05ms、ログ書き込み分離で p99 2794 → 1606ms(-42%)。

設計の根拠・代替案の比較・計測方法は [RELIABILITY.ja.md](RELIABILITY.ja.md) にまとめた。

### リアルタイムチャット

ログインすると(ゲストはニックネームを決めるだけですぐ入場)ロビーに入り、左のルーム
一覧から選ぶか、新しく作って入室する。ルーム一覧は人数とともにリアルタイムで更新され、
ルーム内では接続者一覧、入力中の表示、入退室の通知、再入室時の直近50件の履歴まで
動作する。

ルームの「作成」と「入室」を分けていない — 存在しない名前で入ればその場で作られ、
最後の一人が退室して会話の記録も無ければ一覧から消える。空のルームを残しておくと、
一度使った名前が延々と溜まっていく。片づける人がいない構成なので、
自動で整理される側を選んだ。

表示される名前と、権限の根拠を分けた。 ルームの削除と「送信の取り消し」は
取り返しのつかない操作なのだが(取り消した対象が画像ならDBのバイト列まで消える)、
最初はその権限をニックネームで判断していた。ニックネームは吹き出し・接続者一覧・
ルーム一覧ですべて公開され、ニックネームの登録はいつでも送り直せるので、他人の名前を
そのまま書いて送れば、他人のルームを消し、他人がアップロードした写真を全員から
消すことができてしまった。そこで表示される名前と権限の根拠を分け、
今はその根拠がアカウントである。会話に見えるのは display_name で、取り消し・削除の
権限はアカウントの user id だけで判断する — 前者は公開されるが後者はセッションクッキー
(httpOnly)が証明するので、名前をそのまま書いて送っても真似できない。ソケットは接続
自体が認証で、ハンドシェイクのセッションクッキーでユーザーを確認し、失敗すれば接続を
拒否する。質問・文書・画像のAPIもすべてこのセッションの後ろにある。例外は2つ —
`/api/metrics`(入るのが集計値だけであり、ログインできない障害を診断する場所なので
開けてある)と`/api/kakao/skill`(呼ぶ側がブラウザではなくカカオのサーバーなので
セッションがあり得ない — 代わりにスキルURLに入れるトークンで確認する)。

ドキュメントQ&Aと同じサーバー・同じポート(4000)を使う。分けなかったのは、
転送方式が違うだけで、運用するプロセスを増やす理由にはならないからだ。
統合してみると、むしろ重複が見つかった — HTTPリクエスト制限とチャットの連投制限が
同じToken Bucketをそれぞれコピーして持っていたので、`server/tokenbucket.ts` ひとつに
切り出して両方で共有するようにした(値だけ用途ごとに変えている)。
ダッシュボードにも、チャットのルーム数・接続者数と連投で弾かれたメッセージ数が
一緒に表示される。

### 画像の送信

ファイル選択、貼り付け(スクリーンショット)、ドラッグ&ドロップの3通りで画像を送れる。
画像はPostgresに `bytea` として保存する。

バイト列はソケットに載せない。 先にHTTPでアップロードし、ソケットにはidだけを送る。
ソケットに載せると、写真1枚がルームの人数分だけ複製されて流れ、
メモリに持っている直近50件の履歴にも画像がそのまま溜まる。

アドレスはサーバーが作る。 アップロードはURLではなくidだけを返す。
クライアントがURLを決められると、`https://evil.example.com/tracker.gif` のような
アドレスをルーム全体に撒いて、そこにいる人のブラウザに他人のサーバーへ
リクエストを送らせることができてしまう。サーバーは受け取ったidが自分の発行した
ものかを確認してから、はじめてアドレスを付ける。

形式は先頭バイトで判別する。 ファイル名もContent-Typeもクライアントが書いて
寄こす値なので信用しない。png/jpg/gif/webpの固定シグネチャを自分で確認し、
SVGは意図的に外した — SVGはXMLなので `<script>` を含められ、同一オリジンから
配信した瞬間に保存型XSSになる。レスポンスには `X-Content-Type-Options: nosniff`
も一緒に付ける。

取得は別のコネクションプールに分離した。 画像の取得はメッセージが表示される
たびに走る頻繁で重い読み取りなので、質問検索用の読み取りプールに載せると、
写真の多いルームひとつがこのプロジェクトの「死守する」と言った経路を飢えさせる。
idがuuidで内容が変わらないため不変キャッシュヘッダを付けており、
DBまで届くのは各画像の初回リクエストだけだ。

### 質問への画像添付

ドキュメントQ&Aでも、チャットと同じく＋ボタン、貼り付け(スクリーンショット)、
ドラッグ&ドロップで画像を付けて質問できる(マルチモーダル生成)。ストレージと
アップロード経路はリアルタイムチャットと共用だ — 先にHTTPでアップロードし、
質問にはidだけを載せる。

GIFは質問でだけ弾く。 アップロードはチャットと共用なのでgifも通るが、Geminiの
画像理解がgifをサポートしていない。ここで濾さないと、アップロードは普通に成功して
質問だけが500で落ちるうえ、ユーザーのミスがLLMのサーキットブレーカーに失敗として
積み上がる — 何人かがgifを上げただけで回路が開き、正常な質問までdegradeされる、
他人のせいで開く回路になってしまう。

拒否ゲートとの関係は上の「わからないことは「わからない」と答えさせる」を参照 —
画像が付けば根拠が画像なので、類似度による拒否はしない。

### 生成器はチェーン — ローカル優先、クラウドは最後の砦

`GENERATORS=ollama,gemini`と書けば先頭から試し、前が失敗すれば次へ移る。
オンデバイス優先、クラウドは最後の砦という構成がenvの1行になる(既定はgeminiのみ)。
組み立ては`server/composition.ts`の1箇所だけで行う — 転送(WebのSSE・カカオ)ごとに
各自で組み立てると、「Webはローカル優先なのにカカオはGeminiだけ」のような、
静かに食い違った2つのシステムになる。

乗り換える境界は「最初の一片の前」だ。 すでにトークンが画面へ流れた後で別の
モデルに乗り換えると、前半が重複し、文体の変わった回答が継ぎ足される。そのときは
フォールバックせず、degrade(出典は残して生成だけ諦める)へ回す。ローカル専用の
サーキットブレーカーも別に置いた — Ollamaが死ぬと、60秒のタイムアウトを毎回待つ
代わりに回路が開いて即座に砦へ向かう。

埋め込みはチェーンではなく固定スイッチ(`EMBEDDER=gemini|ollama`)だ。生成と違い、
埋め込みは文書と質問が同じモデルでなければならないので(ベクトル空間が違えば検索が
無意味)、フォールバックが不可能であり、切り替えたら文書を再アップロードする必要が
ある。

### カカオトークチャットボットアダプタ

同じRAGエンジンを、カカオトークのオープンビルダースキルWebhook
(`/api/kakao/skill/<トークン>`)としても公開している。検索・拒否・degradeの方針は
すべてコアが決めるので、Webで拒否される質問はカカオトークでも同じ文言で拒否される。

Webとの決定的な違いは「いつ送るか」だ。 SSEは断片を流せばよいが、オープン
ビルダーは5秒以内に完成したJSONを1つ要求し、ストリーミングがない。そこでイベント
ストリームを時間予算(既定3.5秒 — カカオまで戻るネットワークの分を残す)の中で集め、
予算内に終われば完全な回答、終わらなければコールバック(非同期の返信)へ回すか、
部分的な回答だけでも届ける。予算の収集器はexpressを知らない純粋関数なので、
偽のイベントだけでテストできる(`kakao.test.ts`)。

rate limitはIPではなくカカオのユーザーidに掛ける — リクエストがすべてカカオの
サーバーIPから来るため、IPごとの制限は「全ユーザー共用」の制限になってしまう。
オープンビルダーにはリクエスト署名(HMAC)がないので、スキルURLに秘密トークン
(`KAKAO_SKILL_TOKEN`)を入れて確認する。実際に使うには、オープンビルダーで
チャンネル・ボットを作り、スキルURLを登録するだけでよい。

### イベント契約を型で固定する

HTTPはパスを間違えれば404がすぐ返るが、ソケットイベントは名前が文字列なので、
`"typing"` を `"typeing"` と書いても何も起きない — エラーすら出ない。
そこでSocket.IOをジェネリクスで包み、`emit`/`on` の名前とpayloadをコンパイル時に
検査させた。SSEイベントも同じ理由でユニオン型に固定しているので、サーバー側で
イベントを追加したときにフロント側の処理漏れが型検査で見つかる。

サーバーはビルド工程を持たず、Nodeが型だけ剥がして実行する(`node index.ts`)。
`tsc` は検査専用として使う(`npm run typecheck`)。

### ストリーミングと一時的なエラーへの対応

回答はSSEでストリーミングし、質問ごとに類似度、トークン使用量、応答時間をDBに記録する。
無料枠のrate limitを考慮して埋め込み(エンベディング)リクエストは分割して送り、
APIが一時的なエラー(429, 5xx)を返した場合は指数バックオフでリトライする。
実際に開発中、埋め込みAPIが503を返して回答が失敗するのを経験して入れた仕組みだ。
逆に400や 404のようにリトライしても無意味なエラーは、すぐユーザーに知らせる。

## 技術スタック

- 言語: TypeScript (サーバー・フロントエンドとも)
- フロントエンド: React (Vite) · SSE (回答のストリーミング受信)
- バックエンド: Node.js + Express + Socket.IO
- DB: PostgreSQL + pgvector
- AI: Gemini API — `gemini-embedding-001`(埋め込み) + `gemini-3.6-flash`(生成)、
  無料枠で動作。任意でローカルLLM(Ollama)を生成チェーンの先頭に(`GENERATORS`)、
  埋め込みの切り替えは`EMBEDDER`
- チャネル: Web (SSE) · カカオトーク オープンビルダースキル (Webhook)
- インフラ: Docker (ローカルのpgvector) · Render (デプロイ) · GitHub Actions (CI)

## 実行方法

1. DBの起動(pgvector同梱、初回起動時にschema.sqlを自動適用)

```bash
docker compose up -d
```

2. サーバー

```bash
cd server
cp .env.example .env   # GEMINI_API_KEY を入力 (https://aistudio.google.com/apikey で無料発行)
npm install
npm run dev
```

サーバーが起動したかは `curl http://localhost:4000/api/health` →
`{"ok":true}` で確認する。

3. フロントエンド

```bash
cd web
cp .env.example .env   # 任意 — ローカルのデモは空のままで動作します
npm install
npm run dev   # http://localhost:5173
```

フロントエンドの環境変数は `web/.env.example` にある。Viteは `web/` 配下の
`.env*` しか読まないため、サーバー側の `.env` に `VITE_` で始まる値を書いても
ビルドには反映されない。今使っている値はダッシュボードの障害注入ボタン用の
`VITE_ADMIN_TOKEN` ひとつだけで、ローカルはループバックなので空のままで構わない。
この値を入れてデプロイするとバンドルに平文で入り、訪問者の誰もが読めるという点だけ
注意(ファイル内の注意書きを参照)。

最初の画面はログインだ — 「ゲストとして入場」でニックネームを決めるだけで、登録なしに
すぐ始められる(ゲストもサーバー上ではアカウント1行なので、以降のロジックに
「アカウントがないかもしれない」という分岐がない)。

`sample-docs/` のドキュメント3つをアップロードして、こんなふうに質問してみる。
(デモアプリは韓国語で応答する)

- 「返金は何日かかる?」(환불은 며칠 걸려?) → ドキュメントを根拠に回答 + 出典を表示
- 「返品の送料は誰が負担する?」(반품 배송비는 누가 부담해?) → 条件ごとに分けて回答
- 「バーチャル口座で注文したけど、入金の期限はいつまで?」
  (가상계좌로 주문했는데 입금 기한이 언제까지야?) → 長いドキュメントから
  該当する断片だけを拾ってくる
- 「フランスの首都は?」(프랑스의 수도는?) → 拒否(ドキュメントにない内容)

前の2つのドキュメントは短いので(単語176個と184個)、チャンクが1つずつしか出ない。
オーバーラップするチャンキングが実際に分かれる様子を見るには、3つ目のドキュメント
(`자주-묻는-질문.md` = よくある質問、単語470個 → チャンク3つ)をアップロードして、
一覧のチャンク数を見るとよい。

リアルタイムチャットは上部の「실시간 채팅(リアルタイムチャット)」タブで確認する。
ブラウザのタブを2つ開き、同じルーム名で入室すると会話が行き来する。
テキストの会話はDBがなくても動くが、画像の送信には `chat_images` テーブルが
必要だ(schema.sqlに含まれている)。

DBスキーマが適用されていない場合(ボリュームを先に作ってしまった場合):

```bash
docker exec -i docchat-db psql -U postgres -d docchat < server/schema.sql
```

## 限界と次にやりたいこと

- 会話コンテキスト(マルチターン)はない。質問単位で動作する。
- PDFはパース品質の問題が大きいため、txt/mdに絞った。
- 検索が埋め込みの類似度ひとつに依存している。BM25キーワード検索を組み合わせる
  ハイブリッド検索を次に試してみたい。
- 拒否のしきい値をログを見ながら手動で調整しているが、評価用の質問セットを
  作って自動で測定するのが次の目標。
- チャット履歴がサーバーのメモリにしかないため、再起動すると消える。段階としては
  ① 現在: 単一サーバーのインメモリ(ルーム·メッセージ·presence·連投防止) →
  ② メッセージをPostgresに永続化してdurabilityを確保 → ③ Socket.IOのRedisアダプタで
  pub/subを追加し、presenceをRedisへ移して、別サーバーに繋いだ利用者にも
  メッセージが届くようにする、という順序を考えている。
  埋め込みキャッシュがインメモリなのと同じ性質の限界だ。
- ログインはあるが、文書単位のアクセス制御がない。セッションが答えるのは「入ってきた
  人か」までで、`documents` に所有者・グループの列がないため、ログインした人は全員
  同じコーパスを見る。ない絞り込みをあるふりにしないため、ストア側のアダプタが範囲
  検索そのものを塞いであるが、その列ができるまでは認可がない状態である。
- サーバーとフロントがイベント契約の型をそれぞれコピーして持っている。今の規模では
  ワークスペース導入のコストの方が大きいため見送り、大きくなったら共有パッケージに
  切り出す予定。
- 検証がまだ単体テストのレベルにとどまっている。ソケットのオリジンやCSRFのように
  実際にサーバーを立てないと確認できない挙動は、今は手で再現して確かめており、
  これを統合テストへ上げるのが次の候補だ。
- デプロイ: Neon(pgvector対応) + Renderの無料枠。フロント(Reactビルド成果物)と
  バックエンドを同じRenderサービス1つにまとめて配信している — web/api.tsと
  realtime/socket.tsが相対パス・同一オリジンを前提にしているため、フロントだけ
  別の静的ホスティングに分けると、そのコードにバックエンドの絶対URLを別途
  埋め込む必要がある。無料枠のためしばらくアクセスがないとサーバーがスリープし、
  起動に時間がかかる(上のライブデモリンク参照)。
